# 한끼픽 — 학식 리뷰 REST API

## 개요

학교 식당 메뉴 정보가 부족한 문제를 풀기 위해 기획한 REST API 기반 서비스입니다. 학생·교직원이 학식 메뉴를 날짜별로 조회하고, 메뉴에 별점과 한줄평 리뷰를 등록·조회·수정·삭제하며, 메뉴별 평균 별점을 확인할 수 있습니다.

`Review` 엔티티에 `rating`(별점), `comment`(한줄평), `nickname`(작성자명) 필드를 두고 `Menu`와 `ManyToOne` 연관관계를 설정해, 실제 학식 리뷰 서비스의 흐름을 API로 구현했습니다.

## 주요 기능 (본인 담당)

- **메뉴별 평균 별점 조회** — `GET /menus/{id}/average-rating`
- **리뷰 수정** — `PATCH /reviews/{id}`
- **리뷰 삭제** — `DELETE /reviews/{id}`
- **전역 예외 처리** — `GlobalExceptionHandler`, `ErrorResponse`

## 사용 기술

`Spring Boot` · `Java` · `Spring Data JPA` · `Swagger`

## 트러블슈팅

### 1. 연관관계에서 대상 리뷰만 골라 평균을 내는 구조가 잡히지 않은 문제

**문제**
메뉴별 평균 별점을 계산해야 하는데, 메뉴와 리뷰가 연관관계로 얽혀 있어 "이 메뉴에 달린 리뷰"만 골라내는 구조를 잡는 데 어려움을 겪었습니다.

**원인**
`Menu` 기준으로 조회한 뒤 연관된 리뷰 목록을 어떤 경로로 가져와야 하는지가 코드로 드러나 있지 않았습니다. 리뷰가 하나도 없는 메뉴를 어떻게 처리할지도 정해져 있지 않았습니다.

**해결**
메뉴 id로 메뉴를 먼저 조회하고, 그 메뉴와 연결된 리뷰 목록의 `rating`만 사용해 평균을 계산했습니다. 리뷰가 없는 경우에는 평균값 `0.0`을 반환하도록 정했습니다. `MenuService`, `MenuController`, `AverageRatingResponse` DTO로 나눠 구현했습니다.

**배운 점**
연관관계를 다루는 감각은 "엔티티에서 무엇을 먼저 꺼내는가"를 정하는 데서 생깁니다. 계산 결과가 없는 상태(리뷰 0건)를 먼저 정해두면 서비스 로직이 단순해집니다.

### 2. 리뷰 수정에서 "무엇을 바꿀 수 있는가"가 흐려진 문제

**문제**
리뷰 수정 시 전체 데이터를 다시 저장하는 방식과 일부만 변경하는 방식이 헷갈렸습니다. 전체를 다시 저장하면 작성자명처럼 유지되어야 할 값까지 요청에 실려야 하고, 값이 빠지면 기존 정보가 사라질 위험이 있었습니다.

**원인**
수정 요청 DTO가 "변경 가능한 값"만 담는다는 원칙이 없었습니다.

**해결**
`ReviewUpdateRequest`에 수정 가능한 `rating`, `comment`만 포함시키고, `Review` 엔티티 내부에 별도 수정 메서드(`Review.update`)를 두어 필요한 값만 변경하도록 설계했습니다. 별점은 1~5 범위만 저장되도록 검증했습니다.

**배운 점**
유지할 데이터와 변경 가능한 데이터를 DTO 경계에서 구분하는 것이 설계의 출발점입니다.

### 3. Controller마다 같은 예외 처리가 반복되는 문제

**문제**
리뷰 수정·삭제·평균 별점 조회에서 존재하지 않는 id, 1~5 범위를 벗어난 별점 같은 예외가 반복적으로 발생했고, 이를 각 Controller에서 처리하면 코드가 중복되고 응답 형식도 흐트러질 수 있었습니다.

**원인**
예외 응답 형식과 처리 위치에 대한 공통 규칙이 없었습니다.

**해결**
`IllegalArgumentException` 발생 시 `400 Bad Request`로 일관되게 응답하도록 `GlobalExceptionHandler`와 `ErrorResponse`를 구현했습니다. 여러 Controller에 흩어져 있던 예외 처리 코드를 한곳으로 모았습니다.

**배운 점**
예외 처리는 기능이 아니라 **API의 계약**입니다. 한곳에서 형식을 정하면 클라이언트가 응답을 예측할 수 있습니다.

### 4. HTTP 메서드의 의미에 맞게 API를 설계하는 문제

**문제**
리뷰 수정과 삭제를 어떤 메서드와 상태 코드로 표현할지가 초기에 불명확했습니다.

**해결**
부분 수정은 `PATCH`, 삭제 성공은 본문 없이 `204 No Content`로 표현하고, `GET`/`PATCH`/`DELETE` 각각의 의미에 맞게 메서드와 URL을 설계했습니다. 담당 API는 Swagger로 성공 케이스와 예외 케이스(잘못된 id, 범위를 벗어난 별점)를 모두 직접 요청해 검증했습니다.

**배운 점**
상태 코드는 장식이 아니라 결과의 의미입니다. Swagger로 예외 케이스까지 직접 호출해 보는 습관이 생겼습니다.

## 성과 및 배운 점

- 담당 4개 기능(평균 별점·수정·삭제·전역 예외 처리)을 Swagger로 정상/예외 케이스 모두 검증
