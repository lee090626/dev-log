# Orato — AI 발표 피드백 서비스

## 개요

발표 주제·제한시간·파일을 입력하면 AI 분석 결과를 제공하고, 이전 기록을 검색·정렬·필터로 다시 탐색할 수 있는 발표 피드백 서비스입니다. 학교 팀 프로젝트에서 프론트엔드를 담당했습니다.

## 주요 기능

- **분석 입력** — 주제·태그·제한시간·파일 업로드와 필수값 검증
- **기록 탐색** — 검색·정렬·필터·페이지네이션으로 이전 분석 조회
- **상세 확인** — 목록 맥락을 유지한 채 모달에서 점수와 피드백 확인

## 담당 역할

- 분석 페이지 UI와 사용자 입력값 검증·예외 처리
- 기록 목록의 검색·정렬·필터·페이지네이션 UI
- 점수 요약과 핵심 피드백 상세 모달
- 마이페이지를 제외한 주요 화면 통합과 스타일 구조 개선

## 사용 기술

`React` · `JavaScript` · `Axios` · `styled-components` · `Vite Proxy`

## 사용자 흐름

```
입력 → 검증 → 분석 요청 → 기록 목록 → 상세 모달 → 다시 탐색
```

## 트러블슈팅

### 1. 빈 입력에서도 분석 요청이 전송되는 문제

**문제**
주제나 파일이 비어 있는 상태에서도 분석 요청이 서버로 나갔습니다. 사용자 입장에서는 아무것도 입력하지 않았는데 실패 응답만 돌아오거나, 잘못된 분석 결과가 만들어질 수 있었습니다.

**원인**
요청 직전의 필수값 검증이 부족해 잘못된 상태가 화면을 벗어나 API 경계까지 그대로 전달됐습니다.

**해결**
주제와 파일을 요청 전에 확인하고, 값이 비어 있으면 요청을 차단한 뒤 입력 위치에 오류 안내를 배치했습니다.

**배운 점**
검증은 화면 편의 기능이 아니라 요청 경계의 일부라는 것. 값이 잘못된 상태는 서버까지 가기 전에 막는 편이 사용자에게도, 디버깅에도 낫습니다.

### 2. 기록 탐색과 상세 확인의 책임이 섞인 문제

**문제**
목록 화면이 검색·정렬·필터와 상세 정보 표시까지 동시에 담당하면서 한 화면의 책임이 계속 커졌습니다. 목록 코드를 고치면 상세 표시가 영향을 받는 식의 결합이 생겼습니다.

**원인**
"목록 화면"과 "상세 화면"의 목적이 다르다는 것을 처음부터 분리하지 않았기 때문입니다. 목록은 훑어보는 화면이고 상세는 읽는 화면인데, 둘을 같은 컴포넌트가 처리했습니다.

**해결**
목록은 탐색에 집중하고, 점수 요약과 핵심 피드백은 상세 모달로 분리했습니다.

**배운 점**
목록 스캔과 상세 읽기의 목적을 분리하니 수정 범위와 유지보수성이 함께 좋아졌습니다.

### 3. 개발 환경의 API 요청 경로가 일관되지 않은 문제

**문제**
개발 환경에서 입력 → 분석 요청 → 기록 조회 → 상세 확인으로 이어지는 요청 경로가 제각각이었습니다.

**해결**
Vite Proxy에 요청 경로를 모아, 입력부터 상세 확인까지 같은 기준으로 연결했습니다.

**배운 점**
요청 경로를 한곳에서 관리하면 화면이 늘어나도 같은 흐름을 유지할 수 있습니다.

## 성과 및 배운 점

- 유효하지 않은 요청을 API 이전에 차단
- 목록 스캔과 상세 읽기의 목적을 분리해 수정 범위와 유지보수성 개선
- 기능 수보다 **사용자가 막히는 지점**과 **화면·요청 경계의 책임**을 먼저 정리하는 경험 확보
