# PartTrip — 여행 플래너 웹

## 개요

여행 성향 진단부터 여행지 선택, 메인 대시보드까지 이어지는 여행 플래너 서비스입니다.
팀 프로젝트에서 **웹 파트를 거의 혼자** 담당했습니다. 웹 디자인을 제외한 화면 구현, 페이지 구조 설계, 컴포넌트 분리, 라우팅, 상태 관리, 입력값 검증, 서버 API 연동, 인증 처리, 반응형 레이아웃, 빌드 환경 설정, Git/GitHub 협업까지 웹 개발 전반입니다.

## 주요 기능

- **인증** — 로그인 · 회원가입 · 비밀번호 찾기/변경, 이메일 인증번호 확인, Google OAuth 로그인
- **여행 성향 진단** — 진단 문항과 결과 화면
- **여행지 선택** — 여행지 목록/선택 화면

## 트러블슈팅

### 1. 메인 페이지가 커지면서 컴포넌트 책임이 불분명해진 문제

**문제**
메인 페이지에 사이드바, 여행지 대표 이미지, 여행지 정보, 오늘의 표현, 환율, 날씨, 축제 일정이 한꺼번에 들어가면서 파일 하나가 너무 커졌습니다. 카드 하나의 스타일을 고치려면 전체 페이지 코드를 다시 봐야 했고, 카드마다 성격은 다른데 테두리·그림자·제목·본문 배치는 비슷하게 반복됐습니다.

**원인**
페이지 컴포넌트가 너무 많은 책임을 가지고 있었습니다. 원래 페이지는 전체 화면을 조립하는 역할이어야 하는데, 세부 UI 렌더링·데이터 표현·스타일 구조까지 한곳에서 처리했습니다. 독립적으로 수정될 수 있는 영역들이 코드상으로는 한 덩어리였기 때문에 수정 범위가 불필요하게 커졌습니다.

**해결**
메인 페이지의 역할을 "위젯을 배치하고 전체 레이아웃을 잡는 것"으로 다시 정의하고, `MainHero`, `TravelInfo`, `Festival`, `TodayInfo`, `Sidebar` 위젯으로 분리했습니다. 각 위젯은 `index.ts`를 통해 필요한 컴포넌트만 노출하고, 페이지는 `@widgets/festival`, `@widgets/main-hero` 같은 public API로만 접근합니다. 카드에서 반복되는 기본 스타일은 `shared/ui/dashboard`로 분리했습니다.

**배운 점**
컴포넌트 분리는 파일을 작게 나누는 일이 아니라 **변경 이유가 다른 코드를 분리하는 일**입니다. 코드 길이가 아니라 책임을 기준으로 판단해야 합니다.

### 2. 페이지가 늘어나면서 라우팅 경로가 흩어질 수 있었던 문제

**문제**
로그인, 회원가입, 비밀번호 변경, 성향 진단, 메인 화면이 추가되면서 `/login`, `/main`, `/sign-up` 같은 경로 문자열이 여러 컴포넌트에 직접 쓰일 수 있었습니다. 경로 이름을 바꾸려면 파일을 전부 찾아야 하고, 문자열이라 오타가 나도 TypeScript가 잡아주지 못합니다.

**원인**
라우팅 경로를 중앙에서 관리하지 않으면 같은 경로가 여러 파일에 중복될 수밖에 없습니다. 로그인 성공 후 이동, 진단 완료 후 이동, 사이드바 메뉴 이동처럼 이벤트 기반 이동이 많아질수록 경로 관리가 더 중요해집니다. 라우터 설정과 페이지 이동 로직이 섞이면 전체 사용자 흐름도 파악하기 어려워집니다.

**해결**
경로는 `src/shared/config/paths.ts`의 `paths` 객체에서 관리하고, 라우터 구성은 `src/app/router/router.tsx`에 `createBrowserRouter`로 모았습니다(`/`, `/login`, `/sign-up`, `/change-password`, `/diagnosis`, `/main`). 이벤트 이후 이동은 `useNavigate`, 일반 이동은 `Link`를 사용했습니다. 로그인 성공 후에는 `replace: true`를 적용해 뒤로 가기로 로그인 화면에 돌아가지 않게 했습니다.

**배운 점**
라우팅은 URL과 컴포넌트를 연결하는 작업이 아니라 **사용자가 서비스를 어떤 순서로 이용하게 할지 설계하는 작업**입니다. 남은 과제는 인증 여부에 따른 보호 라우트였습니다.

### 3. 프론트엔드 폼 데이터와 서버 API 형식이 달랐던 문제

**문제**
화면에서는 `email`, `id`, `password`처럼 이해하기 쉬운 이름을 썼는데, 서버 회원가입 API는 `userMail`, `userId`, `userPwd`, `myCountry`, `signUpDivision` 형식을 요구했습니다.

**원인**
화면에서 쓰는 데이터 모델과 서버로 보내는 데이터 모델의 역할이 다르다는 점을 처음부터 분리하지 않았습니다. 구분하지 않으면 컴포넌트가 UI 처리뿐 아니라 서버 전송 형식까지 책임지게 되고, 서버 필드명이 바뀔 때 화면 컴포넌트를 모두 고쳐야 합니다.

**해결**
인증 API 요청을 `src/shared/api/auth.ts`에 모으고, 화면용 타입(`SignUpRequest`)과 서버 전송용 타입(`SignUpPayload`)을 분리했습니다. 변환은 API 함수 내부에서 수행하고, `myCountry: 'KR'`, `signUpDivision: 'USER'` 같은 고정값도 API 계층에서 붙입니다. 로그인 응답은 `LoginResponse` 타입으로 정의해 `accessToken` 구조를 코드에 드러냈습니다.

**배운 점**
화면 데이터와 서버 DTO 사이에 **변환 계층**을 두면 변경 지점이 하나로 모입니다. 정적 데이터로 남아 있던 대시보드 영역을 API로 옮길 때도 같은 방식으로 View Model과 응답 구조를 구분할 계획이었습니다.

### 4. 로그인 이후 요청에 토큰이 포함되지 않아 401 오류가 발생한 문제

**문제**
로그인 API는 정상이고 `accessToken`도 받았는데, 이후 인증이 필요한 요청에서 계속 401 Unauthorized가 발생했습니다.

**원인**
토큰을 저장하는 것과 저장된 토큰을 요청에 쓰는 것은 별개의 과정입니다. `localStorage`에 저장했다고 모든 요청에 자동으로 붙지 않으며, `Authorization: Bearer {token}` 헤더를 각 API 함수에서 직접 작성하면 누락되기 쉽습니다. 일반 로그인과 Google OAuth 로그인처럼 방식이 여러 개면 토큰 저장 방식도 달라져 인증 흐름이 갈라질 수 있었습니다.

**해결**
공통 Axios 인스턴스 `apiClient`에 request interceptor를 추가해, 요청 전에 `localStorage`의 `accessToken`을 읽어 `Authorization` 헤더에 자동으로 붙였습니다. 저장 키는 `ACCESS_TOKEN_KEY` 상수로 관리해 로그인 폼과 API 클라이언트가 같은 키를 쓰도록 했고, Google OAuth 성공 시에도 서버가 반환한 토큰을 같은 방식으로 저장해 로그인 방식과 무관하게 이후 흐름을 통일했습니다.

**배운 점**
인증은 로그인 성공 여부만 확인해서는 안 되고 **토큰 발급 → 저장 → 헤더 첨부 → 만료 처리 → 로그아웃**까지 전체 흐름으로 봐야 합니다. 다음 단계로 401 응답 시 자동 재로그인 유도나 토큰 제거 response interceptor를 남겨뒀습니다.

### 5. 비동기 폼의 단계와 오류 상태가 복잡해진 문제

**문제**
회원가입은 `기본 정보 입력 → 인증번호 확인`, 비밀번호 재설정은 `이메일 → 인증번호 → 새 비밀번호`로 단계가 나뉘는데, 단계마다 입력값 검증·서버 요청·오류 메시지·버튼 비활성화·다음 단계 이동을 모두 처리해야 했습니다. 요청 중 버튼을 여러 번 누르거나 서버 오류가 화면에 제대로 표시되지 않으면 사용자는 무엇이 문제인지 알 수 없었습니다.

**원인**
모든 입력을 각각 `useState`로 관리하면 필드가 늘수록 상태와 핸들러가 증가하고 검증 규칙도 화면마다 중복됩니다. 요청 진행 상태와 단계 상태가 섞이면 조건문이 복잡해집니다. 서버 오류도 문자열, `{ message }`, 일반 Error 등 형태가 제각각이라 화면 표시를 일관되게 만들기 어려웠습니다.

**해결**
폼 상태와 검증은 React Hook Form으로 관리하고(`register`, 필수 입력·정규식·최소 길이·사용자 정의 검증), 공통 검증 규칙과 입력값 정제 함수를 `shared/lib/authValidation.ts`로 분리해 로그인·회원가입·비밀번호 변경에서 재사용했습니다. 단계는 boolean 여러 개 대신 `credentials | verification`, `email | verification | password` 같은 명확한 문자열 상태로 관리했습니다. 요청 중에는 `formState.isSubmitting`으로 버튼과 입력을 비활성화했고, 오류는 `getErrorMessage`에서 Axios 오류·일반 Error·알 수 없는 오류를 구분해 문자열로 변환했습니다. 메시지 영역에는 `aria-live="polite"`를 적용했습니다.

**배운 점**
비동기 UI는 성공하는 경우만 생각하면 안 되고 **요청 전 검증 → 요청 중 상태 → 성공 후 이동 → 실패 후 재시도**가 모두 사용자 흐름에 포함됩니다. 지금은 지역 상태와 React Hook Form으로 충분했지만, 여러 페이지가 서버 상태를 공유하게 되면 TanStack Query 같은 도구를 검토할 지점입니다.

### 6. 전역 스타일 충돌과 반응형 레이아웃 깨짐 문제

**문제**
넓은 화면에서는 괜찮았지만 화면 폭이 줄면 카드가 좁아지거나 텍스트와 아이콘이 겹칠 수 있었고, 고정 폭을 쓰는 인증 화면은 모바일에서 영역이 벗어날 수 있었습니다. 전역 선택자 중심으로 스타일을 작성하면 한 화면을 고쳤는데 다른 화면까지 영향을 받았습니다.

**원인**
데스크톱 기준으로 레이아웃을 맞추다 보니 작은 화면에서의 배치 변화를 고려하지 못했고, 카드 크기·간격·사이드바 위치·텍스트 길이가 고정값으로 지정돼 있었습니다. 색상·그림자·테두리·radius도 각 파일에 직접 작성해 디자인 일관성을 유지하기 어려웠습니다.

**해결**
Styled Components로 스타일을 컴포넌트 단위로 분리하고(페이지 전용은 해당 page slice의 `*.styles.ts`, 위젯 전용은 위젯 내부), 공통 색상·배경·테두리·radius·shadow·font family는 `appTheme`으로 정의해 `ThemeProvider`로 공급했습니다. 전역 스타일은 box-sizing, body 여백, 글꼴, 배경처럼 앱 전체에 필요한 최소 항목만 담당하게 하고, 메인 화면·사이드바·카드·인증 폼·여행지 선택 화면에는 미디어 쿼리를 적용했습니다.

**배운 점**
반응형은 화면을 줄여 보는 작업이 아니라, 공간이 바뀔 때 **어떤 요소를 먼저 유지하고 어떤 요소를 아래로 내릴지 정하는 설계**입니다.

### 7. 개발 서버와 외부 API 사이에서 CORS 문제가 발생한 문제

**문제**
로컬 Vite 개발 서버에서 외부 ngrok 주소의 서버 API를 호출할 때 CORS preflight 요청이 차단됐습니다. 처음에는 프론트엔드 요청 코드가 잘못된 것처럼 보였습니다.

**원인**
개발 서버와 API 서버의 origin이 다르면 브라우저가 CORS 정책을 확인합니다. 서버 응답에 현재 프론트엔드 origin을 허용하는 `Access-Control-Allow-Origin` 헤더가 없으면 차단됩니다. 요청 주소는 `.env`의 `VITE_API_BASE_URL`을 따르고 있었고, Vite 설정에는 개발용 프록시가 없었습니다. 즉 프론트엔드 코드만으로 해결할 수 있는 문제가 아니었습니다.

**해결**
`.env`, `src/shared/api/client.ts`, `vite.config.ts`를 확인해 요청 주소와 프록시 설정 여부를 점검하고, 프론트엔드 로직 문제가 아니라 네트워크·서버 설정 문제임을 확인했습니다. ngrok 경고 페이지 문제는 공통 Axios 헤더에 `ngrok-skip-browser-warning`을 설정해 줄였습니다. CORS 자체는 서버에서 허용 origin을 설정하거나 개발 서버에 프록시를 두는 방향으로 정리했습니다.

**배운 점**
통신 오류를 만나면 요청 함수만 보지 말고 **Network 탭 · 요청 origin · 서버 응답 헤더 · 환경 변수 · 프록시 설정**을 함께 봐야 합니다. 개발·운영 주소, 허용 origin, 인증 헤더 정책은 사전에 맞추는 것이 낫습니다.

### 8. 빌드는 성공했지만 번들 크기 경고가 발생한 문제

**문제**
`npm run lint`와 `npm run build`는 모두 통과했는데, 일부 이미지·SVG 자산 크기가 크고 JavaScript 청크가 500kB를 초과한다는 경고가 출력됐습니다.

**원인**
메인 대표 이미지와 일부 SVG의 용량이 컸고, 라우터가 각 페이지를 정적 import하고 있어 첫 접속 시 여러 페이지 코드가 하나의 번들에 포함될 수 있었습니다. 외부 UI 라이브러리와 인증 라이브러리도 초기 번들에 영향을 줬습니다. 빌드가 성공하는 것과 성능 최적화가 끝난 것은 다른 문제였습니다.

**해결 방향**
이번 단계에서는 기능 구현과 빌드 안정성을 우선해 경고를 개선 항목으로 분리했습니다. 이후 `React.lazy`와 동적 import로 라우트 단위 코드 스플리팅, PNG → WebP/AVIF 변환과 SVG 최적화, 미사용 패키지 정리, 번들 분석 도구로 큰 의존성 확인을 계획으로 남겼습니다.

**배운 점**
빌드 성공은 최종 품질이 아닙니다. 큰 이미지나 외부 라이브러리를 추가할 때마다 번들 크기 영향을 함께 보는 습관이 필요합니다.

## 성과 및 배운 점

- 공통 구조(`app`/`pages`/`widgets`/`shared`)를 만들고, 인증 API를 실제로 연결하고, 메인 화면을 위젯 단위로 분리하고, 반응형까지 적용
- React Hook Form, Axios 인터셉터, Styled Components ThemeProvider, React Router로 화면 구현을 넘어선 서비스 구조 경험
- ESLint `no-restricted-imports`로 FSD 계층 규칙을 강제해 **혼자 작업해도 구조가 무너지지 않게** 만든 것이 가장 효과가 컸음
- "완료했다"를 **화면 구현 / API 연결 / 인증 적용 / 오류 처리 / 반응형** 단계로 나눠 공유해야 팀이 오해하지 않는다는 것을 체감
- 남은 것: 대시보드 정적 데이터의 실제 API 전환, 인증 기반 라우트 가드, 테스트 코드, 번들 최적화
