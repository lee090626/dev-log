도담도담 앱 내부 패키지 `aid-kit`의 버그를 찾아 원인을 정리한 분석 과제입니다. 코드를 고치는 과제가 아니라 **어디가 왜 틀렸는지**를 스크린샷과 함께 남기는 과제였기 때문에, 이 기록의 "수정 방향"은 분석에서 도출한 것이고 실제 반영 여부는 확인하지 않았습니다.

## 트러블슈팅

### 1. error.ts에서 키와 값이 일치하지 않아 생긴 typo 에러

**문제**
에러 코드 정의에서 키와 값이 서로 다른 쌍으로 묶여 있었습니다. 코드상으로는 문제없이 빌드되지만, 특정 에러를 던지면 의도한 코드가 아니라 다른 코드가 반환됩니다.

**원인**
코드 → 메시지 매핑을 손으로 작성하면서 키와 값의 짝이 어긋났습니다. 같은 문자열이 양쪽에 반복되는 구조라 컴파일러도 잡아주지 못합니다.

**수정 방향**
키-값 쌍을 한 번만 정의하고(예: 상수 객체의 키를 그대로 값으로 쓰는 형태) 타입으로 묶어, 짝이 어긋나면 타입 단계에서 걸리게 만듭니다.

**배운 점**
문자열을 두 번 쓰는 구조는 반드시 한쪽이 틀어집니다. 정의는 한 곳, 참조는 타입으로.

### 2. ACK·SYNC가 callback을 반환하지 않아 프로토콜이 깨지는 문제

**문제**
`ACK`와 `SYNC` 요청에 대해 앱 쪽에서 callback을 mount하지 않으면 `NOT_SUPPORT`로 응답이 나갔습니다. 지원하지 않는 요청으로 분류되면서 프로토콜 흐름 자체가 깨졌습니다.

**원인**
`ACK`·`SYNC` 처리 경로가 callback을 반환하는 구조를 전제로 작성되어 있었습니다. callback이 없으면 "처리할 수 없는 요청"이라는 판정으로 흘러갔습니다.

**수정 방향**
`ACK`·`SYNC`는 callback 유무와 무관하게 처리되는 경로로 분리하고, callback이 없을 때는 `NOT_SUPPORT`가 아니라 정상 응답(또는 명시적 no-op)으로 끝나게 합니다. 두 요청이 "지원 대상"인지 판정하는 조건과 "callback이 있는지"를 같은 조건으로 쓰지 않는 것이 핵심입니다.

**배운 점**
"지원하지 않음"과 "이번에 할 일이 없음"은 다른 상태입니다. 두 상태를 한 분기로 합치면 프로토콜이 조용히 끊깁니다.

### 3. SYNC 복원 시 ACK id가 undefined가 되는 문제

**문제**
`SYNC` 복원 경로에서 `ACK` id가 `undefined`로 넘어갔습니다.

**원인**
`enqueue`가 두 가지 형태로 호출됩니다. 위쪽 호출은 **task 객체**를 넘기므로 `task.req.id`로 참조해야 하고, 아래쪽 호출은 **`BridgeResponse` 객체**를 넘기므로 `res.id`로 참조해야 합니다. 그런데 `enqueue` 내부 코드는 `BridgeResponse` 객체만 참조 가능하게 작성되어 있어, task 객체가 들어온 경우 id를 꺼내지 못했습니다.

**수정 방향**
`enqueue`가 받는 대상의 타입을 명확히 구분(오버로드 또는 두 함수로 분리)하고, 각 경로에서 id를 꺼내는 접근자를 통일합니다. 같은 함수가 두 종류의 객체를 받는 구조 자체가 이 버그의 원인이므로, 호출부를 정리하는 편이 재발을 막습니다.

**배운 점**
같은 이름의 함수가 서로 다른 타입을 받으면, 내부 구현은 반드시 둘 중 하나에만 맞춰집니다. 나머지 하나는 조용히 `undefined`가 됩니다.

## 성과 및 배운 점

- 브리지 프로토콜에서 "지원하지 않음 / 처리할 일 없음 / 처리 실패"를 구분하지 않으면 흐름이 끊긴다는 것을 세 건 모두에서 확인
- 세 버그의 공통 원인은 **타입 경계의 모호함**(문자열 중복 정의, 두 타입을 받는 함수, 상태 구분 없는 분기)
- 버그를 고치기 전에 "어느 경계에서 값이 어긋났는지"를 먼저 찾는 방식으로 접근
